ticketloop · architecture

How the loop works — and who drives each step

The harness owns only the framework, the git plumbing, and a few safety rails; the model does the actual work of every step — using each project's own skills, tools, MCP, and CLI. Triage first decides whether any action is needed at all (a sign-off / approval is skipped), then routes a ticket to one of four kinds — answer a question, export data, open/refresh a PR, or investigate a bug (reproduce → root-cause before planning). On the change/bug path, every gating step (verify, review, ship, and the opt-in dev steps) returns a pass/fail verdict; ship drives the PR to green CI, and a run that also passes deploy-dev/verify-dev finishes deployed. Projects run in parallel (one ticket each); any run is checkpointed so it resumes where it stopped, and can be paused system-wide or per ticket. All Linear I/O uses each project's own API key, so multiple client workspaces never cross.

The fix loop, in detail

The first fix runs once. Then the gates run in sequence — verify → review → ship — and each must pass before the next runs: the moment one fails, its findings go straight back to fix (no point reviewing or shipping a change verify already rejected). Bounded by maxFixIterations, with a no-progress backstop. Provider quota is checked at every stage; an exhausted provider checkpoints the run and waits instead of ending the fix loop. Ship is the last gate: its instruction opens/updates the PR, watches the PR's CI, and fixes until green (no CI → mergeable → pass). The harness never reads CI — how to watch and wait is the ship instruction's business.

One signal: the verdict

# harness appends this to every gating step VERDICT: pass VERDICT: fail — <reason>

verify, review, and ship each end with this one line — last wins · synonyms ok · missing → fail-open. CI lives inside ship: the instruction runs gh pr checks, fixes reds, and only passes when green. No CI → immediately mergeable → pass. The harness stays out of it.

Multi-repo — prepare all, ship the dirty ones

A project can be a folder of sibling repos. The harness mirrors a worktree + branch for every repo up front (so the model sees them side-by-side and can touch any), the model edits whichever the ticket needs, then it ships one PR per changed repo. The guardrail runs over all repos; untouched repos' empty branches are deleted on success.

The model decides which repos a ticket touches — the harness never pre-assigns. A change may legitimately span repos (an API field in backend + the UI in frontend). If some repos ship and others fail, the run is partial.

Scheduling — parallel, resumable, pausable

Each poll launches at most one run per project, all projects at once. A project with a run in flight is skipped until it finishes, so two runs never fight over the same repo's worktree — while several tickets across different projects progress together. Quota is shared: the governor gates every launch.

Checkpoint & resume

Every completed stage is cached to a per-ticket checkpoint (with the worktree/branch it used). A run interrupted by a dropped connection, a rate limit, a restart, or a pause resumes at the exact stage it stopped — earlier stages replay from cache (0 tokens) and the same worktree is reattached. A new human comment invalidates the checkpoint (the ask changed → start fresh).

Pause / resume

System-level (pause/resume) halts the whole loop at the next stage boundary; ticket-level pauses just one ticket while the other projects keep running. Because of one-per-project, resuming a ticket whose project is busy warns and queues it — it resumes once that project frees.

Who drives what

The model runs every step and, inside a step, reaches for that project's own git / gh / checks / skills / MCP as its instruction directs. The harness stays thin: it discovers work, does the deterministic git plumbing, enforces the guardrails, and records history.

design principle

Provide the framework, not the method. The harness fixes the sequence, does the mechanical git (worktree, branch off main, cleanup), and holds the safety rails — the quota gate, the off-limits-path check over every repo, and “open a PR, never merge.” Everything about how a step is done — which repos a ticket touches, where export data comes from, whether a check passes — is the model's, shaped by a per-step instruction. Each project is isolated: its own repo, its own Linear key, its own credentials — one client's work can never reach another's. Trade-off: more flexible and project-adaptive, slightly less deterministic than a hard-coded harness — which is why the guardrails, git plumbing, and per-project keys stay in plain code.
